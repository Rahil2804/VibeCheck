# Phase 2A Design - SQLite Saved Profiles

## Goal

Add explicit local saved profiles so a user can preserve useful neighborhood analyses and reopen them later. This creates the backend foundation for compare mode, refresh controls, source freshness, and provenance without adding accounts or public sharing.

## Scope

Phase 2A includes:

- SQLite-backed local storage for saved `AnalyzeResponse` payloads.
- Explicit save flow after a successful analysis.
- Backend endpoints to create, list, read, and delete saved profiles.
- Searchable saved-profile metadata: ID, place label, coordinates, confidence level, created timestamp, updated timestamp, and source status summary.
- Frontend save action and a compact saved profiles panel.
- A visible synthesis status so local development makes it clear whether OpenAI was used, skipped, or failed with deterministic fallback.
- README and `PLAN.md` updates for the new local database behavior.

Phase 2A excludes:

- Accounts or authentication.
- Public share URLs.
- Hosted persistence.
- Compare mode calculations.
- Profile refresh/regeneration controls.
- Deep provenance drawers for individual claims.

## Backend Design

Create a small SQLite persistence layer in `backend/storage.py`. It will own database connection setup, schema initialization, and CRUD functions for saved profiles. The database path will default to `data/vibecheck.db` and can be overridden with `SQLITE_PATH` for tests or local experimentation.

The first table will be `saved_profiles`:

- `id`: text primary key generated by the backend.
- `place_label`: text for list display.
- `coordinates_json`: nullable JSON text for latitude/longitude.
- `confidence_level`: text copied from the response.
- `source_statuses_json`: JSON text copied from the response source statuses.
- `response_json`: full serialized `AnalyzeResponse`.
- `created_at`: UTC ISO timestamp.
- `updated_at`: UTC ISO timestamp.

The API surface:

- `POST /profiles` accepts an `AnalyzeResponse` JSON body and returns saved-profile metadata plus the stored response.
- `GET /profiles` returns a newest-first list of metadata and source summaries, not the full response payload for every row.
- `GET /profiles/{id}` returns the saved metadata and full `AnalyzeResponse`.
- `DELETE /profiles/{id}` deletes a saved profile and returns a small success response.

The storage layer should initialize tables at FastAPI startup/import time for local development. It should not require a separate migration command during Phase 2A.

## AI Synthesis Visibility

Today the backend silently falls back if OpenAI is unavailable or fails. Phase 2A should make this visible without turning failures into hard errors.

Add a top-level `synthesis` field to `AnalyzeResponse` with a small `SynthesisStatus` model:

- `status`: one of `used`, `skipped`, or `fallback`.
- `model`: the configured OpenAI model when synthesis is attempted, otherwise `null`.
- `message`: safe plain-English status for the UI.

The status values distinguish:

- `used`: OpenAI returned a schema-valid profile.
- `skipped`: no `OPENAI_API_KEY` was available.
- `fallback`: OpenAI was attempted but failed, so deterministic profile was used.

The UI should show `synthesis.status` and `synthesis.message` alongside confidence/source status information. It should not expose API keys, raw prompts, model errors containing secrets, or full provider exception details.

## Frontend Design

After `POST /analyze` returns data, show a Save button near the profile header or selected-place actions. Saving should call `POST /profiles` with the analysis response and then show a saved state.

Add a saved profiles panel that can:

- Load saved profile metadata from `GET /profiles`.
- Reopen a saved profile by calling `GET /profiles/{id}` and rendering the stored response.
- Delete a saved profile with confirmation or a clear delete action.

The panel should stay compact and app-like. It should not become a marketing or dashboard page. The map-first experience remains the first screen.

## Error Handling

If SQLite cannot initialize or write, the API should return a clear 500 response for profile save/list/read/delete endpoints. Analyze should still work without saved profiles.

If a saved ID does not exist, `GET /profiles/{id}` and `DELETE /profiles/{id}` should return 404.

If the frontend save call fails, keep the analyzed profile visible and show a retryable save error. Failed saves should not force the user to rerun analysis.

## Testing

Backend tests should use a temporary SQLite path or isolated test database and should not read the developer's local `data/vibecheck.db`.

Required tests:

- Saving an `AnalyzeResponse` returns an ID and persisted metadata.
- Listing profiles returns newest-first metadata without requiring full response expansion.
- Reading a saved profile returns the original response payload.
- Deleting a saved profile removes it and subsequent reads return 404.
- OpenAI synthesis status reports `skipped`, `used`, and `fallback` through injected synthesizer behavior.

Frontend manual verification should cover:

- Save after a successful analysis.
- Reopen a saved profile.
- Delete a saved profile.
- Save failure state.
- OpenAI synthesis status display.

## Data And Privacy

Saved profiles are local-only in Phase 2A. The SQLite file should be ignored by git. The app should not store API keys, raw OpenAI prompts, raw provider payloads, or credentials in SQLite. Stored response JSON is acceptable because it matches what the app already displays locally.

## Acceptance Criteria

- A user can analyze a place, explicitly save it, close/reopen the local app, and retrieve the saved profile from SQLite.
- Tests cover storage CRUD and synthesis status behavior.
- Analyze still works if the database is unavailable.
- Saved profiles are local-only and no account/share URL concepts are introduced.
- `PLAN.md` clearly marks Phase 2A completion status and leaves compare/provenance as future Phase 2 slices.
