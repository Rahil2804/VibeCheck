# Phase 2C Design - Provenance And Source Depth

## Goal

Make VibeCheck feel more trustworthy and analytically grounded by showing which sources support major neighborhood claims, while beginning to enrich the normalized source payload that feeds deterministic scoring and optional OpenAI synthesis.

This phase should improve the product's honesty, not just its wording. The AI should still summarize only supplied normalized data. Source support and provenance should be generated by backend code from source statuses and normalized adapter outputs, not invented by the model.

## Scope

Phase 2C includes:

- Typed provenance models for source-backed claims.
- Backend provenance generation for deterministic and synthesized profiles.
- A frontend "Source support" section that explains why major claims appear.
- Saved reports preserving provenance in the stored `AnalyzeResponse`.
- One conservative source-depth pass focused on non-sensitive lifestyle/access signals.
- Tests for provenance schema, pipeline generation, saved-report persistence, and UI rendering contracts.

Phase 2C excludes:

- Safety/crime claims.
- School ratings or family-status related signals.
- Protected-class or protected-class-proxy scoring.
- Compare mode.
- Public share URLs.
- Accounts or cloud sync.
- Asking OpenAI to invent citations or inspect raw provider payloads.

## Product Shape

The selected-location analysis panel should continue to prioritize fit, overview, scores, highlights, confidence, and source statuses. Provenance should appear as a compact trust layer near the confidence/source area.

The UI should answer:

- "What source supported this score or statement?"
- "Was this directly supported, inferred from a normalized signal, or unavailable?"
- "Which sources are missing or thin?"

It should not become a dense audit console. The first version can show a small list of supported claim areas, such as:

- Overview: generated from available access, housing, Census, and discussion signals.
- Walkability score: supported by access source.
- Affordability score: supported by housing source, or marked unavailable.
- Demographic context: supported by Census source, or marked unavailable.
- Trajectory: uncertain because trend sources are thin.

## Data Model

Replace the loose `NeighborhoodProfile.provenance: dict[str, Any]` with typed models.

### `ProvenanceSupport`

Allowed values:

- `direct`: a claim or field came directly from a normalized source field.
- `inferred`: a claim was computed from one or more normalized source fields.
- `unavailable`: the relevant source was missing, empty, errored, or too thin.

### `ProvenanceItem`

Fields:

- `claim_id`: stable machine-readable ID, such as `vibe.walkability` or `context.median_household_income`.
- `label`: short user-facing label, such as `Walkability score`.
- `summary`: one sentence explaining source support or missing data.
- `support`: one of `direct`, `inferred`, or `unavailable`.
- `sources`: list of `SourceName` values that contributed to the claim.
- `source_fields`: list of normalized field names used, such as `access.walkability`.

### `ProfileProvenance`

Fields:

- `items`: list of `ProvenanceItem`.

`NeighborhoodProfile` should include:

```python
provenance: ProfileProvenance = Field(default_factory=ProfileProvenance)
```

This keeps provenance attached to the profile and therefore automatically persists inside saved reports.

## Backend Design

Add `backend/provenance.py` as the backend owner of claim-support metadata.

The module should expose:

```python
def build_profile_provenance(
    source_data: dict[SourceName, dict[str, Any]],
    statuses: list[SourceStatus],
) -> ProfileProvenance:
    """Return source support metadata for major profile claims."""
```

The function should:

- Inspect normalized source data, not raw provider responses.
- Produce stable provenance items for major fields whether data is present or absent.
- Mark a claim `direct` when a profile field maps directly to a normalized source field.
- Mark a claim `inferred` when the app computes a score or summary from normalized fields.
- Mark a claim `unavailable` when supporting source data is empty, errored, or missing.
- Use status messages and missing fields to make summaries plain-spoken.

Initial claim IDs:

- `overview`
- `vibe.walkability`
- `vibe.transit_access`
- `vibe.affordability`
- `vibe.quiet`
- `vibe.social_scene`
- `context.median_age`
- `context.median_household_income`
- `context.population_density`
- `trajectory`

### Pipeline Behavior

`analyze_neighborhood()` should build provenance after source statuses and source data are available.

For deterministic fallback profiles:

- `_build_profile()` should accept provenance or the pipeline should attach it immediately after profile construction.
- Deterministic pros/cons and trajectory should stay cautious when provenance is thin.

For synthesized profiles:

- The OpenAI schema should remain focused on profile text and scores.
- The backend should attach `ProfileProvenance` after synthesis returns.
- OpenAI should not be asked to create provenance items.

If synthesis fails and the deterministic fallback is used, provenance generation should still run.

## Source-Depth Pass

Phase 2C should enrich one low-risk source area first. The best target is `access`, because it directly supports lifestyle fit and avoids sensitive safety/fair-housing concerns.

The access source can remain deterministic/local in tests and still be designed for future provider-backed data. It should normalize fields such as:

- `walkability`
- `transit_access`
- `food_social`
- `parks_outdoors`
- `daily_needs`
- optional `nearby_categories` counts when available

For this phase, the implementation may use deterministic coordinate/query heuristics or mocked adapter outputs in tests rather than introducing a new paid provider. The key improvement is that downstream profile generation and provenance know which normalized fields exist and how they support claims.

Housing and Census can receive light provenance mapping without deeper live fetching:

- `housing.affordability` supports affordability.
- `census.median_age`, `census.median_household_income`, and `census.population_density` support demographic context.

## Frontend Design

Add a compact provenance component near confidence, for example `Provenance.jsx` or an inline section in `Profile.jsx`.

The UI should show:

- Section title: `Source support`
- A short list of provenance items.
- Each row includes label, support type, source chips, and summary.
- Use neutral labels: `Supported`, `Inferred`, `Unavailable`.
- Keep unavailable items visible but visually muted.

The UI should not show raw payload JSON or provider internals. It should use normalized field names only when helpful.

Example row:

```text
Walkability score
Inferred - access
Based on normalized access.walkability signal.
```

When no provenance exists, the UI should omit the section rather than rendering an empty card.

## Error Handling

Provenance generation must never break analysis. If a source fails, provenance should mark affected claims as unavailable and rely on `source_statuses` for the failure details.

If an old saved report lacks typed provenance, the frontend should still render the profile normally and skip the Source support section.

If OpenAI synthesis returns a valid profile but source data is thin, provenance should make that thinness clear rather than making the synthesis look more certain.

## Privacy And Safety

Provenance must not expose raw provider payloads, API keys, prompts, user notes, or hidden internal data.

Freeform preference profile notes remain local-only and should not be sent to OpenAI in Phase 2C.

Fit scoring must continue to use only neutral preference inputs and non-protected neighborhood signals.

No safety/crime, school, family-status, race, religion, disability, sex, national origin, or equivalent proxy claims should be introduced.

## Testing

Backend tests should cover:

- `ProvenanceItem` and `ProfileProvenance` JSON serialization.
- Provenance generation for present access, housing, Census, and Reddit fields.
- Unavailable provenance when source data is empty or a status is error/empty.
- Pipeline attaches provenance to deterministic fallback profiles.
- Pipeline attaches backend-generated provenance to synthesized profiles.
- Saved reports persist and restore provenance.
- OpenAI payload schema does not require the model to create provenance.

Frontend tests or source-contract checks should cover:

- `Profile.jsx` renders a `Source support` section when provenance items exist.
- UI uses support labels and source names.
- UI omits the section when provenance is missing.
- Build still passes.

Manual verification should cover:

- Generic analysis with thin data shows unavailable provenance items without breaking the result.
- Saved-profile analysis shows the same provenance behavior.
- Saved report reopen preserves Source support.
- Confidence and source statuses remain visible.

## Acceptance Criteria

- Analyze responses include typed provenance for major profile claims.
- Provenance is generated by backend code from normalized source data and source statuses.
- OpenAI synthesis does not invent source support.
- The analysis panel shows a compact Source support section.
- Missing or failed sources produce unavailable provenance, not broken UI.
- Saved reports preserve provenance.
- At least one low-risk source area, preferably access, has richer normalized fields for provenance and profile support.
- Existing generic analysis, saved-profile analysis, preference profiles, and saved report flows continue working.
- Phase 2C does not introduce safety/crime, school, protected-class, account, cloud sync, compare mode, or public share features.
